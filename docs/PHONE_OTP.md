# ورود و ثبت‌نام با موبایل — ملی‌پیامک

مسیر اصلی رابط، شماره موبایل ← کد پیامکی شش‌رقمی ← ایجاد نشست است. حساب جدید با نام و نقش معلم/دانش‌آموز پس از اثبات مالکیت شماره ساخته می‌شود؛ رمز عبور لازم نیست و رمز ساختگی قابل استفاده هم ساخته نمی‌شود. حساب موجود همان نقش ذخیره‌شده را حفظ می‌کند. نقش والد فقط از دعوت معتبر معلم، منطبق با شماره و رابطهٔ آموزشی معتبر ایجاد می‌شود؛ منشی/سوپرادمین از ثبت‌نام عمومی قابل انتخاب نیستند.

ورود با رمز حساب قبلی برای سازگاری در لینک ثانویه مانده است. انتخاب روش در localStorage تنها ترجیح رابط است و مجوز سرور ایجاد نمی‌کند. تست‌های قدیمی صریحاً همین روش را انتخاب می‌کنند؛ تست OTP با storage خالی مسیر اصلی را بررسی می‌کند.

## تنظیم محرمانه

- `MELIPAYAMAK_USERNAME`: نام کاربری سرویس
- `MELIPAYAMAK_PASSWORD`: رمز یا credential وب‌سرویس مورد پذیرش پنل
- `MELIPAYAMAK_OTP_BODY_ID`: شناسهٔ الگوی خدماتی تأییدشده با دقیقاً یک متغیر برای کد
- `AUTH_OTP_SECRET`: ۳۲ بایت تصادفی base64، یکسان در همهٔ پردازش‌های وب، مستقل از کلید صف ایمیل

این مقادیر فقط در secret محیط سرور قرار می‌گیرند؛ هرگز `NEXT_PUBLIC_` یا Git یا پیام چت نباشند. پس از تنظیم، برنامه restart شود. بدون تنظیم معتبر، API خطای 503 و رابط خطای روشن نشان می‌دهند؛ هیچ OTP ثابت، نمایشی، logشده یا fallback تولیدی وجود ندارد.

Adapter موجود `MelipayamakProvider` از HTTPS و متد الگویی `BaseServiceNumber` استفاده می‌کند؛ قرارداد از [کد رسمی SDK ملی‌پیامک](https://github.com/Melipayamak/melipayamak-node/blob/master/src/sms/restAsync.js) بررسی شده است. پکیج قدیمی SDK نصب نشده؛ transport کوتاه، بدون logging credential و با timeout ده ثانیه است. پذیرش تنها با RetStatus=1 و receipt مثبت معتبر محسوب می‌شود. پذیرش API به معنی تحویل گوشی نیست. وضعیت ارسال واقعی و سازگاری credential/الگوی پنل: **BLOCKED — EXTERNAL SERVICE** تا تنظیم و آزمون روی شماره مجاز مالک.

## قرارداد و امنیت

`POST /api/auth/otp/request {phone}`: شماره فارسی/عربی/+98/0098 نرمال می‌شود. پاسخ موفق فقط challengeId، مهلت ۳۰۰ ثانیه و فاصله ارسال مجدد ۶۰ ثانیه دارد؛ هیچ کدی به مرورگر برنمی‌گردد. درخواست موجود/ناموجود یکسان است و هر دو همان پیامک را می‌گیرند. ارسال شکست‌خورده challenge را باطل می‌کند؛ retry خودکار پیامک ندارد تا هزینه و ارسال تکراری ناخواسته نسازد.

`POST /api/auth/otp/verify {phone,challengeId,code,name?,role?,invitationToken?}`: challenge به شماره و شناسه و HMAC-SHA256 وابسته است؛ کد خام در MongoDB ذخیره نمی‌شود. پنج حدس مجاز، انقضای پنج دقیقه، یک‌بارمصرف و مصرف/ایجاد حساب/دعوت/نشست در تراکنش MongoDB اجرا می‌شوند. حدس غلط بیرون از rollback خطا ثبت می‌شود تا شمارنده واقعاً افزایش یابد. رقابت دو تأیید فقط یک نشست می‌سازد.

حد ارسال هر شماره: یک‌بار در دقیقه و پنج‌بار در ساعت، پایدار در MongoDB؛ هر IP پنج درخواست در ده دقیقه، تأیید پانزده درخواست در ده دقیقه. limiter IP موجود پردازش‌محور است؛ برای چند وب‌سرور باید محدودکنندهٔ مشترک لبه نیز تنظیم شود. TTL حذف فیزیکی ممکن است دیرتر باشد؛ اعتبار منطقی با expiresAt بررسی می‌شود.

کوکی نشست HttpOnly، SameSite=Strict و در HTTPS تولیدی Secure است. حساب غیرفعال وارد نمی‌شود. audit فقط رویداد و شناسه حساب دارد. phoneVerified صرفاً اثبات دریافت کد روی شماره است؛ اثبات سن، شخص، مالک قانونی سیم‌کارت، رضایت یا اختیار سرپرستی نیست.

## تست و محدودیت

`tests/integration/phone-otp.test.ts` از MongoDB واقعی و SMS dependency کنترل‌شده استفاده می‌کند؛ مسیر ملی‌پیامک با transport کنترل‌شده آزموده می‌شود. `tests/e2e/phone-otp.spec.ts` مسیر عمومی موبایل، ثبت‌نام، نشست، refresh و logout را پوشش می‌دهد. این تست‌ها اثبات ارسال پیامک واقعی نیستند. هیچ درخواست پولی یا پیامک واقعی در این بسته ارسال نشده است.
